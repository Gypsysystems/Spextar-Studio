# F3 — Topic drafts and structured authoring

## Authoritative live contract

The existing approved Supabase project provides `public.topic_drafts`:
`topic_id`, `content` (JSON object), `revision`, `updated_at`, `updated_by`.
Reads/inserts/updates use the authenticated browser client and existing RLS.
There is intentionally **no save RPC**, no new schema, and no client migration.

- A missing row means no saved body, not a demo/fixture fallback.
- First save inserts `topic_id`, structured `content`, and the current
  authenticated identity as `updated_by`. The database establishes revision **1**.
- Later saves update only `topic_id = selected Topic AND revision = last read`.
  The trigger advances the revision. The client never assigns revision or time.
- `INSERT/UPDATE … RETURNING` (`select(...).maybeSingle()`) consumes the resulting
  trigger-produced row/revision atomically, avoiding a racing second read.
- A competing first insert (unique violation) or zero-row conditional update is
  a conflict. No upsert, force-save, automatic rebase or speculative RPC exists.
- Scope checks verify identity, selected project, document and Topic before
  access; write checks require explicit Project Admin/Author membership.
  RLS remains authoritative. Reviewer/Viewer/inherited read-only members cannot
  write even if they call the service outside the UI.

Existing database duplication operations already copy draft content; the Author
loads the draft by the resulting Topic identity, for both document copies and
Topic subtree copies. No client-side duplication of body rows is performed.

## Content format and the current editor

New bodies use an extensible document object:

```json
{
  "type": "doc",
  "version": 1,
  "content": [
    { "type": "paragraph", "content": [{ "type": "text", "text": "Body text" }] }
  ]
}
```

Slice 2A replaces the Slice 1 textarea with the open-source Tiptap editing engine.
The SPEXTAR domain module owns the persisted JSON contract independently of
Tiptap. Root extensions/metadata and version 1 are preserved. Unversioned `doc`
objects remain unversioned. JSONB equality is canonicalized so object-key
reordering is not mistaken for an edit.
Topic title/status/kind/settings remain the independent F2 metadata flow.
Body/content keys remain prohibited in metadata settings.

### Slice 2A supported editing subset

- Paragraphs, H1–H3, bold, italic, underline, strike, inline code, code blocks,
  blockquotes, bullet/ordered lists, hard breaks and horizontal rules.
- Links with safe HTTP(S), mailto, tel or relative URLs; link insert/edit/remove
  uses the current selection. Active/script URLs and unsafe targets are blocked.
- Tables with row/column insertion/deletion, header toggling and table deletion.
  Existing valid cell spans, widths and alignment survive load/save. Inconsistent
  grids, overlap, missing cells, oversized spans or more than 128 columns are
  rejected before the engine can silently repair them.
- Undo/redo operates within the active editor. Autosave acknowledgements do not
  reset selection/history. Explicit server reload/recovery/discard resets history
  so undo cannot resurrect a superseded remote draft.
- The same editor is used in demo mode with in-memory structured content. Demo
  body edits remain session-only and never call Supabase or backend recovery.

Every structural block/container/table node receives `attrs.id`, including
paragraphs inside cells/list items. Text/marks are anchored by their containing
block plus a text range. Existing IDs survive typing, formatting, undo/redo and
move operations. Splits, inserted/copied nodes and new table cells receive unique
IDs; pasted external HTML does not import IDs. Opening legacy JSON without IDs
does **not** write to the backend: IDs are persisted with an explicit edit or
recovery save.

**Identity is Topic-scoped:** future references must use `(Topic UUID, node ID)`.
The existing database duplication operations intentionally copy JSON unchanged;
the same node ID in a different Topic is not a collision. There is no schema/RPC
change for this slice.

Unknown versions, node types, attributes or marks are shown as verbatim,
read-only JSON; no editor normalization, replacement save or plain-text fallback
is allowed. Unsupported recovery copies cannot replace supported server content
and vice versa. Future extensions must explicitly extend the SPEXTAR validator
and bridge before enabling edits. Root metadata is never handed to Tiptap to
reinterpret. Plain-text previews/word counts are derived only for presentation,
not as a persistence format.

Only MIT-licensed open-source Tiptap packages are used (`react`, `core`, `pm`,
`starter-kit`, `extension-table`, locked at 3.32.0). No Cloud, paid extension,
collaboration or hosted editor integration is present. See the distributed
editor license notices in `public/licenses/editor-notices.txt`.

Basic table tools are intentional; cell merge/split/resizing UI, syntax
highlighting, rich paste of unsupported nodes and advanced schema features are
not included. The existing dark semantic theme and locally served Inter apply
to every editor surface, including code and read-only JSON.

### Slice 2B — semantic technical callouts

The existing Author toolbar adds **Note**, **Tip**, **Caution** and **Warning**
controls. Select a paragraph or supported block range and choose a kind to wrap
it. Inside a callout, choosing a kind changes that same container without
replacing its content or identity. **Remove callout** unwraps the content rather
than deleting it. Enter in an empty final paragraph exits the callout. Standard
undo/redo, text formatting, lists, links, code and tables remain available.
Labels are generated from the semantic kind, not editable body text. The
accessible HTML uses a labeled `note` role, never an intrusive live alert.
Dark surfaces, Inter, visible text labels and restrained accent borders distinguish
types without relying on color alone. The toolbar remains keyboard-navigable and
horizontally scrollable on mobile.

SPEXTAR owns the additive version-1 JSON node:

```json
{
  "type": "callout",
  "attrs": { "id": "topic-scoped-node-id", "kind": "warning" },
  "content": [
    {
      "type": "paragraph",
      "attrs": { "id": "paragraph-node-id" },
      "content": [{ "type": "text", "text": "Disconnect power before maintenance." }]
    }
  ]
}
```

`kind` must be exactly `note`, `tip`, `caution` or `warning`; non-empty supported
block content is required. Unknown kinds, missing/invalid attributes, invalid
children and unsupported nested content preserve the original JSON read-only.
The same node identity and root metadata/version rules apply. Older Studio
clients that do not understand callouts fail closed through their existing
unsupported-content guard, rather than flattening the new nodes.

Callouts use only the existing authenticated `topic_drafts.content` path,
revision-safe saves, recovery and duplication behavior. No database migrations,
RPCs, grants, Auth settings or editor dependencies are added. Project Admin/Author
can edit; Reviewer/Viewer can read only. Demo callouts stay in memory and are
discarded when the demo Author workspace is remounted; they do not write backend
drafts or browser recovery.

### Slice 2C — Topic-local Find and Replace

The Author toolbar's **Find and replace** button opens a compact search panel.
Ctrl/Cmd+F or Ctrl/Cmd+H opens it when focus is inside this editor. Enter and
Shift+Enter in the Find field navigate next/previous, wrapping at either end.
Escape closes the panel and restores focus to the toolbar button.

- Search is literal (not regular expressions), Unicode-aware and case-insensitive
  by default; **Match case** enables case-sensitive matching.
- Matches cross adjacent inline formatting runs, but never paragraph/heading/code
  block boundaries, hard breaks or table cells. Body text in lists, callouts,
  tables and code is included. Topic titles, metadata, URLs stored as link
  attributes and generated callout labels are not searched.
- Highlights and the current match are view-only decorations. Search, navigation,
  case changes and closing the panel never write body JSON or recovery copies.
- **Replace current** changes the active match; **Replace all** replaces the
  original non-overlapping matches in one undoable edit, not recursively matching
  newly inserted text. Replacement is single-line literal text; HTML, `$1` and
  `$&` are not interpreted. An empty replacement removes matched text only.
- Replacements retain structural nodes, durable IDs, callout kind, table settings,
  code language, link targets and root metadata/version. Unmatched text/marks
  remain unchanged. Across different marked runs, replacement characters consume
  each original run's character length, with overflow inheriting the final run's
  marks; shorter replacements naturally remove the unused text runs. Surrogate
  pairs are not split at replacement formatting boundaries.
- Search is available to Reviewer/Viewer. Replacement additionally requires the
  existing editable Project Admin/Author draft state; it is disabled while loading,
  read-only, conflicted, awaiting recovery, or otherwise blocked. The engine command
  also rejects replacement in read-only mode or during active IME composition.
- Unknown/malformed saved documents continue to show their original read-only JSON;
  no partial-document search/replace or normalization is attempted.
- Search state is local to the mounted Topic editor. Topic navigation resets it.
  A genuine server reload resets matches; ordinary autosave echoes preserve it.
  Query, replacement text, highlights and current match are never persisted.
- Highlighting is capped at 10,000 matches to bound browser work. If more exist,
  the panel explicitly asks for a narrower query and disables Replace all rather
  than silently replacing only a subset. The Find field allows up to 2,000 characters.

Replacement uses the existing editor update/controller path, including debounce,
revision checks, explicit retry/reload, identity-scoped recovery and cache cleanup.
Demo replacements remain session-only. No database table, migration, RPC, content
schema change or dependency is introduced.

### Advanced technical tables

The existing contextual Table toolbar now provides:

- Insert table; add/delete rows and columns; explicit Delete table.
- Merge selected cells and Split cell. Selection must be a valid rectangle
  containing only data cells or only header cells. Mixed header/data merges,
  merges intersecting external spans and any result outside Studio's supported
  structured JSON model are disabled, not silently normalized.
- Toggle the first header row, first header column, or selected cells' header
  type, with pressed-state feedback. A first-row/column header boundary cannot
  bisect an existing spanning cell. Selected-cell toggling follows the existing
  engine behavior: if any selected cell is a header, convert the selection to
  data cells; otherwise convert to headers.
- Select cell, row, column or table from labelled, keyboard-accessible controls.
  Alt+Shift+arrow keys extend/contract a rectangular cell selection. Pointer
  multi-cell selection remains supplied by the open-source table engine.
- Tab/Shift+Tab navigate cells without body writes. Editable Tab at the final
  cell appends one row and moves into it as one undoable operation. Shift+Tab at
  the first cell uses native focus navigation. Read-only Tab never creates rows.
- Each explicit structural table operation starts its own undo event. Undo/redo
  restores content, spans, formatting and IDs without appending an extra paragraph.

Merge retains the top-left cell's ID and all nonempty selected content, including
paragraph IDs/marks, callouts, links and code blocks. Removed cell/container IDs
are intentionally removed; undo restores them. Split retains the original cell's
content/ID in the top-left cell and creates uniquely identified empty cells; it
does not attempt to guess how previously merged content should be redistributed.
Fully spanned rows may legitimately contain no own cells; the grid validator
accepts these only when rowspans cover the entire row. Empty uncovered or jagged
rows, invalid spans, unknown attributes and unknown nodes remain losslessly
read-only. Grid width retains its existing 128-column bound.

Deleting every remaining row/column is disabled: use the explicit Delete table
control instead. Candidate commands are checked in isolation before dispatch;
availability checks and rejected operations must not modify document JSON,
revision or recovery. Reviewer/Viewer may select cells but all mutation controls
and commands remain read-only. Project Admin/Author table edits use the existing
topic-draft autosave, revision conflict/retry, recovery, reload and duplication
paths. Existing conflict behavior is unchanged, including retaining local edits
without force-overwriting the newer server revision. Demo table edits stay in
memory only.

No database tables, migrations, Supabase settings, dependencies or persisted
content schema version are added. The frozen Author panels and responsive dark
toolbar patterns remain; on small screens toolbar controls scroll horizontally.

Validation includes grid/span boundaries, row/column/header operations, safe
merge/split, durable IDs, exact undo/redo, read-only and IME guards, malformed
JSON, zero-write selection/navigation, backend controller saves/recovery/errors/
conflicts, and demo isolation. Chromium acceptance covers the actual Author UI
at 1280px and 390px using controlled Supabase HTTP responses, not live RLS testing.

## Autosave, conflicts and navigation

- A 700 ms debounce exposes loading, no saved body, unsaved, saving, saved revision,
  error and conflict states through an accessible live status.
- Writes serialize per identity/Topic, retain newer keystrokes during an
  in-flight save and use the confirmed new revision for the next save.
- Pending saves survive normal Topic/route changes within the identity-scoped
  cache. Clean unobserved controllers are evicted. Identity/cache teardown stops
  pending work; there is no blind write-on-unmount or background automatic retry.
- A clean editor refreshes on window focus. Dirty editors do not silently adopt
  a new revision. F2 metadata refetches do not reset active body edits.
- Retry uses the same last-read revision. Reload displays the latest server
  body while retaining unmatched recovery copies. Only an explicit **Restore
  recovery** adopts the displayed server revision for that local copy; it still
  fails if a different writer changes the row before the conditional save.
- Confirmed deletions stop related draft controllers and remove related local
  recovery. Existing conservative F2 deletion rules/relationships remain unchanged.

## Browser crash recovery and privacy

Every edit is synchronously copied to localStorage before network autosave.
Copies are scoped to the approved backend, signed-in user, project, document,
Topic and browser tab; content never enters demo storage or auth tokens.
The browser tab identifier uses sessionStorage and survives refresh.

After reload, a different local copy is offered for explicit restore/discard;
it is never submitted automatically. The saved server body remains visible.
All different copies are retained conservatively, even if timestamps suggest an
older copy, because local/server clocks may differ. Multiple tab copies are
kept separately. A matching confirmed server save/read clears matching copies,
not newer or different intervening edits. Discard removes only the copies shown.

Recovery is **unencrypted browser-local content**, not a security boundary or a
cross-device backup. Use a trusted browser. Explicit sign-out/session loss or a
different signed-in identity clears the previous identity's copies. Organization
changes alone do not erase them. Read-only roles do not receive recovery actions.
Blocked/quota-exhausted storage produces a visible warning; server saving remains
available, but keep the tab open until a successful save. Recovery does not clear
on failed or uncertain network writes. An ambiguously committed save is reconciled
by reloading and comparing against the confirmed server content.

## Scope exclusions and migration provenance

No comments, approvals, release/version publishing, reusable content, media,
variables/conditions, cross-references or collaboration are added.
No F0/F1/F2 RPC, grants, policies, Auth settings or schema are changed.

The live table/column availability was checked read-only with the publishable key,
and insert/revision semantics were explicitly supplied by the project owner.
Applied F3 migration identities and exact SQL are **not discoverable through
the currently available public metadata access**. No timestamps/SQL are invented
or claimed source-controlled. A verified authorized export is still required for
an exact migration-history baseline.

## Verification boundaries

Automated service/controller/Author tests cover conditional table writes,
competing inserts, stale updates, debounce/serialization, recovery choices,
uncertain network outcomes, role/scope rejection, cleanup and demo isolation.
The complete pre-existing suite remains a regression gate.
Slice 2A adds JSON round-trip/root metadata, durable IDs, formatting/table/link
commands, read-only behavior, unsupported-content safety and structured recovery
tests. Native browser typing/caret behavior is verified separately from JSDOM's
limited contenteditable/selection simulation.
Slice 2B adds callout JSON/HTML round-trips, malformed-content rejection, stable
IDs, kind changes, unwrap/undo/redo, keyboard exit, role guards, demo isolation,
and full Author adapter save/reload plus recovery/conflict/error regression tests.
Slice 2C adds literal/Unicode/case-sensitive search, block/inline boundaries, match
navigation, formatting-preserving current/all replacement, empty/HTML-like text,
undo/redo, bounded highlighting, role guards, zero-write search, demo isolation,
and Author adapter/recovery/retry/concurrency tests. Desktop/mobile browser checks
also cover Topic switching, copied structured content, unknown JSON and keyboard use.

Browser acceptance can exercise the real production frontend, Supabase adapter,
sign-in UI, refresh, conflict/error/role states and responsive views against a
controlled HTTP backend. Such checks are not proof of live Supabase RLS/trigger
execution. Report live authenticated testing separately; never bypass RLS or use
a service-role key to turn a controlled browser test into a claimed live pass.
