# F3 Slice 1 — Topic draft persistence

## Authoritative live contract

The existing approved Supabase project provides `public.topic_drafts`:
`topic_id`, `content` (JSON object), `revision`, `updated_at`, `updated_by`.
Reads/inserts/updates use the authenticated browser client and existing RLS.
There is intentionally **no save RPC**, no new schema, and no client migration.

- A missing row means no saved body, not a demo/fixture fallback.
- First save inserts `topic_id`, structured `content`, and the current
  authenticated identity as `updated_by`. The database establishes revision **1**.
- Later saves update only `topic_id = selected Topic AND revision = last read`.
  The trigger advances the revision. The client never assigns revision or time.
- `INSERT/UPDATE … RETURNING` (`select(...).maybeSingle()`) consumes the resulting
  trigger-produced row/revision atomically, avoiding a racing second read.
- A competing first insert (unique violation) or zero-row conditional update is
  a conflict. No upsert, force-save, automatic rebase or speculative RPC exists.
- Scope checks verify identity, selected project, document and Topic before
  access; write checks require explicit Project Admin/Author membership.
  RLS remains authoritative. Reviewer/Viewer/inherited read-only members cannot
  write even if they call the service outside the UI.

Existing database duplication operations already copy draft content; the Author
loads the draft by the resulting Topic identity, for both document copies and
Topic subtree copies. No client-side duplication of body rows is performed.

## Content format and the current editor

New bodies use an extensible document object:

```json
{
  "type": "doc",
  "version": 1,
  "content": [
    { "type": "paragraph", "content": [{ "type": "text", "text": "Body text" }] }
  ]
}
```

The current textarea round-trips plain paragraphs, whitespace and blank lines.
Root extensions are preserved. Unversioned `doc` objects are supported. Unknown
versions, nodes, paragraph attributes and text marks are retained intact and
view-only instead of being flattened and losing structure. JSONB equality is
canonicalized so object-key reordering is not mistaken for an edit.
Topic title/status/kind/settings remain the independent F2 metadata flow.
Body/content keys remain prohibited in metadata settings.

## Autosave, conflicts and navigation

- A 700 ms debounce exposes loading, no saved body, unsaved, saving, saved revision,
  error and conflict states through an accessible live status.
- Writes serialize per identity/Topic, retain newer keystrokes during an
  in-flight save and use the confirmed new revision for the next save.
- Pending saves survive normal Topic/route changes within the identity-scoped
  cache. Clean unobserved controllers are evicted. Identity/cache teardown stops
  pending work; there is no blind write-on-unmount or background automatic retry.
- A clean editor refreshes on window focus. Dirty editors do not silently adopt
  a new revision. F2 metadata refetches do not reset active body edits.
- Retry uses the same last-read revision. Reload displays the latest server
  body while retaining unmatched recovery copies. Only an explicit **Restore
  recovery** adopts the displayed server revision for that local copy; it still
  fails if a different writer changes the row before the conditional save.
- Confirmed deletions stop related draft controllers and remove related local
  recovery. Existing conservative F2 deletion rules/relationships remain unchanged.

## Browser crash recovery and privacy

Every edit is synchronously copied to localStorage before network autosave.
Copies are scoped to the approved backend, signed-in user, project, document,
Topic and browser tab; content never enters demo storage or auth tokens.
The browser tab identifier uses sessionStorage and survives refresh.

After reload, a different local copy is offered for explicit restore/discard;
it is never submitted automatically. The saved server body remains visible.
All different copies are retained conservatively, even if timestamps suggest an
older copy, because local/server clocks may differ. Multiple tab copies are
kept separately. A matching confirmed server save/read clears matching copies,
not newer or different intervening edits. Discard removes only the copies shown.

Recovery is **unencrypted browser-local content**, not a security boundary or a
cross-device backup. Use a trusted browser. Explicit sign-out/session loss or a
different signed-in identity clears the previous identity's copies. Organization
changes alone do not erase them. Read-only roles do not receive recovery actions.
Blocked/quota-exhausted storage produces a visible warning; server saving remains
available, but keep the tab open until a successful save. Recovery does not clear
on failed or uncertain network writes. An ambiguously committed save is reconciled
by reloading and comparing against the confirmed server content.

## Scope exclusions and migration provenance

No comments, approvals, release/version publishing, reusable content, media,
variables/conditions, cross-references or structured-editor toolbar are added.
No F0/F1/F2 RPC, grants, policies, Auth settings or schema are changed.

The live table/column availability was checked read-only with the publishable key,
and insert/revision semantics were explicitly supplied by the project owner.
Applied F3 migration identities and exact SQL are **not discoverable through
the currently available public metadata access**. No timestamps/SQL are invented
or claimed source-controlled. A verified authorized export is still required for
an exact migration-history baseline.

## Verification boundaries

Automated service/controller/Author tests cover conditional table writes,
competing inserts, stale updates, debounce/serialization, recovery choices,
uncertain network outcomes, role/scope rejection, cleanup and demo isolation.
The complete pre-existing suite remains a regression gate.

Browser acceptance can exercise the real production frontend, Supabase adapter,
sign-in UI, refresh, conflict/error/role states and responsive views against a
controlled HTTP backend. Such checks are not proof of live Supabase RLS/trigger
execution. Report live authenticated testing separately; never bypass RLS or use
a service-role key to turn a controlled browser test into a claimed live pass.
